# Research: Automated Prompt Iteration System

## Technology Decisions

### Backend Framework: FastAPI
**Decision**: Use FastAPI for Python backend API

**Rationale**:
- Modern async Python framework with excellent performance
- Automatic OpenAPI schema generation (contract-first development)
- Built-in request validation using Pydantic models
- Native async support for LLM API calls (avoid blocking)
- Type hints enable better IDE support and fewer runtime errors

**Alternatives Considered**:
- Flask: Simpler but lacks native async, requires extensions for OpenAPI
- Django REST Framework: Overkill for single-user local app, heavier footprint

### Frontend Framework: React + TypeScript
**Decision**: React with TypeScript for frontend

**Rationale**:
- Component-based architecture matches UI requirements (reusable charts, forms, tables)
- Large ecosystem for charting (Recharts), forms (React Hook Form), state (Zustand)
- TypeScript provides type safety matching backend Pydantic models
- Fast local development server, mature testing tools (Jest, RTL)

**Alternatives Considered**:
- Vue.js: Smaller ecosystem for data visualization
- Svelte: Less mature testing ecosystem, fewer third-party integrations

### LLM Orchestration: LangChain
**Decision**: Use LangChain for LLM provider abstraction

**Rationale**:
- Unified interface for multiple providers (OpenAI, Anthropic, custom)
- Built-in retry logic, rate limiting, streaming support
- Conversation memory management out of the box
- Active community, well-documented

**Alternatives Considered**:
- Direct API calls: Requires manual provider abstraction, retry logic
- LiteLLM: Lighter but less conversation management support

### Local Storage: SQLite
**Decision**: SQLite for structured data, file system for blobs

**Rationale**:
- Zero-configuration embedded database, perfect for local-first apps
- ACID transactions for iteration state consistency
- Full-text search for conversation transcripts
- Portable single-file database (easy backup/export)
- Store projects, iterations, eval results; store large conversation transcripts as JSON files

**Alternatives Considered**:
- JSON files: No ACID guarantees, complex querying, concurrency issues
- PostgreSQL/MySQL: Overkill for local app, requires separate server process

### Credential Storage: Python cryptography + Fernet
**Decision**: Fernet symmetric encryption for LLM API keys

**Rationale**:
- Cryptography library is industry-standard Python crypto
- Fernet provides authenticated encryption (confidentiality + integrity)
- Key derived from machine-specific identifier (OS-level keyring future enhancement)
- Meets FR-050 requirement for encrypted local storage

**Alternatives Considered**:
- Plain text config: Violates constitutional Principle V (security risk)
- OS keyring (keyring library): Over-engineering for v1, add later if needed

### Testing Strategy
**Decision**: pytest (backend), Jest + RTL (frontend), OpenAPI contract tests

**Rationale**:
- pytest fixtures enable TDD workflow (setup test scenarios, then implement)
- OpenAPI schema auto-generated by FastAPI enables contract-first testing
- React Testing Library enforces user-centric test writing
- Constitutional TDD compliance: tests before implementation

**Testing Layers**:
1. **Contract tests**: Validate API request/response against OpenAPI schema
2. **Integration tests**: Full optimization workflow (create project → iterate → export)
3. **Unit tests**: Evaluation scoring, prompt rewriting logic, LLM retry handling

### Conversation Simulation Approach
**Decision**: LLM-based simulator with persona prompts

**Rationale**:
- Use LLM to generate realistic multi-turn user responses
- Simulator prompted with test scenario description + user persona
- Allows diverse conversation patterns without hardcoded scripts
- Supports custom test scenarios per FR-004

**Implementation**:
- Separate "simulator LLM" instance (can be different model than target)
- Track conversation state, enforce turn limits per scenario (FR-012)
- Generate user messages based on scenario context + conversation history

### Evaluation Agent Design
**Decision**: LLM-based evaluator with structured scoring prompts

**Rationale**:
- Use LLM to score conversations against criteria (persona consistency, tone, safety)
- Structured prompt with scoring rubric, examples, output format (JSON score + explanation)
- Supports custom criteria with user-provided rubrics (FR-008)

**Scoring Process**:
1. For each criterion: LLM evaluates conversation → score (0-100) + text explanation
2. Average scores across test scenarios (FR-019)
3. Check each criterion's average ≥ threshold (FR-020)

### Prompt Rewriting Strategy
**Decision**: LLM-based rewriter with feedback incorporation

**Rationale**:
- Use LLM to generate improved prompts based on evaluation feedback
- Input: current prompt + failed criteria + evaluation explanations
- Output: rewritten prompt addressing specific failures
- Tracks prompt lineage for traceability (FR-024)

**Rewriter Prompt Design**:
- Include original prompt, evaluation scores, failure explanations
- Instruction to preserve working aspects, improve failing dimensions
- Version tracking via parent_id linkage

## Architecture Decisions

### API Design Pattern: REST with Resource-Oriented URLs
**Decision**: RESTful API following resource conventions

**Endpoints**:
- `GET /projects` - List projects
- `POST /projects` - Create project
- `GET /projects/{id}` - Get project details
- `DELETE /projects/{id}` - Delete project
- `POST /projects/{id}/iterations` - Start new iteration
- `GET /projects/{id}/iterations` - List iterations
- `GET /iterations/{id}/conversations` - Get iteration conversations
- `POST /projects/{id}/export` - Export reports (JSON/CSV per FR-032)

**Rationale**:
- Standard REST patterns reduce learning curve
- Resource hierarchy matches domain model
- OpenAPI auto-generation from FastAPI

### State Management: Backend-Driven
**Decision**: Backend manages all iteration state, frontend polls/subscribes

**Rationale**:
- Iteration execution is long-running (LLM API calls)
- Backend orchestrates: simulate → evaluate → rewrite loop
- Frontend displays real-time status via WebSocket or polling (FR-035)
- Simplifies frontend (stateless), backend ensures consistency

### Error Handling Strategy
**Decision**: Graceful degradation with detailed error context

**Error Scenarios**:
1. **LLM API unavailable**: Retry with exponential backoff, fail iteration after N retries
2. **Rate limit hit**: Queue requests, wait and retry (FR-047)
3. **Max iterations reached**: Mark project as "incomplete", save best iteration (FR-025)
4. **API credential expired**: Surface error to user with re-auth flow

**Implementation**:
- Structured error responses with recovery hints
- Log all API errors for debugging (FR-044)
- Surface errors in UI with actionable next steps

### Performance Optimization
**Decision**: Async execution, background tasks, caching

**Strategies**:
1. **Async LLM calls**: Use FastAPI async endpoints + aiohttp for concurrent API requests
2. **Background tasks**: Run iteration loops in background (Celery or FastAPI BackgroundTasks)
3. **Caching**: Cache LLM responses for identical inputs (optional future enhancement)

**Rationale**:
- Single iteration involves multiple LLM calls (simulate, evaluate, rewrite)
- Async prevents UI blocking, improves throughput
- Meets FR-046 (progress feedback) via status polling

## Best Practices Integration

### Configuration Management
**Config Files**:
- `config/default.yaml`: Default settings (iteration limits, timeouts)
- `.env` (gitignored): User-specific settings (LLM provider preferences)
- `data/credentials.enc`: Encrypted API keys (Fernet encrypted)

**Environment Variables**:
- Override config values via env vars (12-factor app pattern)
- Support development vs. production modes (verbose logging, etc.)

### Logging and Observability
**Logging Strategy**:
- Structured JSON logs for API calls, errors, iteration events
- Log levels: DEBUG (development), INFO (production)
- Persist logs to `logs/` directory for post-mortem analysis

**Metrics to Log** (FR-044):
- LLM API call latency, token usage, costs
- Iteration duration, success/failure rates
- Evaluation score distributions

### Security Considerations
**API Key Protection**:
- Never log API keys or credentials
- Encrypt credentials at rest (Fernet)
- Validate user input to prevent injection attacks (Pydantic validation)

**Input Validation**:
- Max prompt length (prevent token overflow)
- Max iteration limit (prevent infinite loops even with user config)
- Sanitize file paths for report exports
